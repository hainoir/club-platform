# 面试讲稿

## 项目定位

可以把这个项目讲成：

- 一个面向校园社团的运营工作流系统。
- 一个体现 App Router、Supabase SSR、复杂状态同步和多步骤业务流的前端项目。
- 一个不仅有页面实现，还有数据库契约和端到端验证意识的工程化作品。

## 30 秒版本

这是一个我主导梳理和实现核心前端链路的校园社团管理系统，技术栈是 Next.js App Router、React、TypeScript 和 Supabase。它的重点不是页面数量，而是登录态同步、值班签到、请假代班审批和工作室自习记录这些真实业务流程。我把首页数据聚合放在服务端，把定位签到、状态同步和复杂交互放在客户端，并且用 Playwright 覆盖了关键路径。

## 90 秒版本

这个项目是一个校园社团运营系统，覆盖登录、成员、活动、值班和工作室自习几个核心场景。我前端侧重点做了几件事。

第一，我把 App Router 的服务端和客户端边界拆清楚了。服务端布局和中间件负责会话校验、首屏用户解析和数据聚合，客户端 Provider 负责长期登录态同步、重水合和路由守卫。

第二，我把首页做成了“服务端先聚合，客户端再交互”的结构。像排班、已批准请假、今日签到和当前用户这些数据，都由 `dashboard-service` 一次并发拉齐；真正需要浏览器能力的值班签到、定位验证和提示反馈，再放到客户端组件里处理。

第三，值班大厅不是把所有逻辑写在一个页面里，而是拆成 `useDuty` 这个门面，再继续拆成签到、请假、代班、钥匙交接几个子域 hooks。这样复杂业务不会失控，后续加规则也更容易定位。

另外，这个项目不是只停留在 UI。像请假和代班通过 `leave_id` 串起来，自习会话通过 RPC 统一做过期清理，这些都让我在做前端的时候也能把数据库契约一起考虑进去。最后我还用 Playwright 覆盖了登录保护、值班、自习和设置等关键流程。

## 3 分钟版本

这个项目是一个基于 Next.js App Router 和 Supabase 的校园社团管理系统。我把它当作一个业务工作流项目来做，而不是一个简单的后台页面集合。系统里最核心的几条链路是登录态同步、首页仪表盘、值班签到、请假代班审批，以及工作室自习在场记录。

在架构上，我比较重视服务端和客户端边界。中间件会统一处理 Supabase 会话续期和受保护路由判断；进入业务页面后，服务端布局先解析当前用户，再把结果交给客户端的 `AppRouteGuard` 和 `AuthProvider` 去接管后续状态同步。这样做的好处是首屏状态稳定，同时客户端还能在标签页切换、焦点恢复和 token 刷新时继续对齐登录态。

首页这块我没有让组件各自发请求，而是专门做了一个 `dashboard-service`。它会在服务端并发读取排班、已批准请假、签到记录、成员信息和当前用户，然后把聚合后的稳定数据结构交给页面。这样页面文件本身就可以保持成视图层，真正依赖浏览器能力的逻辑，比如定位签到、节流、重复签到检查和错误提示，再放到 `DashboardSignInWidget` 这种客户端组件里。

值班模块是我认为最能体现工程拆分的一部分。它不是一个大而全的 hook，而是 `useDuty` 先建立共享上下文，再把排班、签到、请假、代班和钥匙交接分别拆到子域 hooks 里。这样每个模块只关心自己那条业务线，但页面对外拿到的还是统一接口。请假和代班这部分我还特别注意了数据库契约，例如普通请假可以直接走 `approve_duty_leave`，但一旦和代班绑定，就必须通过 `leave_id` 和代班流程一起收口，避免两条路径重复审批。

工作室自习这条线也比较适合展开。因为值班签到和自习记录的语义不同，所以我没有把它们塞进一张表，而是让 `duty_logs` 和 `studio_sessions` 分开建模。前端读取在场列表前，会先调用 `expire_studio_sessions` 这个 RPC 清理过期会话，然后再把 duty 和 self-study 两条来源合并成统一展示结果。这种做法能保证规则统一，不会把时间窗口逻辑散落在各个组件里。

最后，验证方面我除了做 lint、typecheck 和 build，也保留了 Playwright 的关键路径测试。对我来说，这个项目的价值不只是做出页面，而是把前端状态、数据库规则和真实业务流程串成一套能解释、能验证、也能继续维护的结构。

## 高频追问与回答

### 1. 为什么用 App Router，而不是把所有逻辑都放客户端？

因为这个项目有明确的首屏鉴权和数据聚合需求。像当前用户、首页排班、签到状态这些内容更适合服务端先拿到，能减少首屏抖动和重复请求；真正依赖浏览器能力的部分，比如定位签到、焦点恢复、标签页可见性同步，再交给客户端组件处理。

### 2. 登录态同步为什么这么复杂？

因为“用户能登录”不等于“前端状态永远正确”。这个项目里既有服务端首屏渲染，也有客户端后续交互，所以需要中间件续期、服务端用户注入、客户端 Provider 监听、Zustand store 持有状态几层一起工作，才能避免刷新、切标签或 token 过期时状态漂移。

### 3. 为什么把值班逻辑拆成这么多 hooks？

因为它本质上是多个子域拼起来的业务系统。排班、签到、请假、代班、钥匙交接虽然都属于值班模块，但它们的读写规则不同、依赖的数据表不同、刷新关系也不同。拆开后每个 hook 只关心自己负责的动作和数据，`useDuty` 再统一对外暴露，维护成本会低很多。

### 4. 你怎么防止重复签到或者伪造签到？

前端会先做时间窗口判断、点击节流和当天已签到检查，减少无意义请求；提交时还要做工作室定位校验；数据库层面 `duty_logs` 也有唯一约束兜底。所以它不是只靠一个按钮状态，而是前端交互约束和数据库事实一起保证。

### 5. 为什么工作室自习要和值班签到分开建模？

因为两者虽然都表示“人在工作室”，但语义不同。值班签到是考勤，有排班和定位约束；自习会话是停留记录，有自己的开始、结束和自动过期规则。如果混在一张表里，前端展示和数据库契约都会越来越混乱。

### 6. 你怎么处理 Supabase RPC 出错这种问题？

我会先区分是前端调用错误，还是数据库函数签名、权限或 schema cache 出了问题。这个仓库里我会先对照 `docs/supabase-rpc-checklist.md`，确认函数存在、参数一致、权限正确，再决定是不是前端 Bug。

### 7. 这个项目你觉得最能体现前端能力的地方是什么？

不是页面样式，而是把真实业务流程拆成稳定结构的能力。包括服务端和客户端边界、状态同步、复杂业务拆 hook、数据库契约对齐，以及最终能用测试把关键路径兜住。
